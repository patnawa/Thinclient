# 1.5.1 candidate validation

Development candidate; not a published release or physical-fleet certification.
The live 1.5.0 server and release have not been changed by this work.

## Implemented scope

- Installer source/tool/configuration preflight, target revalidation, flushed
  boot-file hash checks, and fatal bootloader/configuration/unmount errors.
- Background network configuration, Wi-Fi, diagnostics, resolution discovery,
  and installer disk discovery with closed-dialog and secret-safe error guards.
- Explicit Lite MMC/SDHCI boot drivers; expanded non-secret hardware inventory.
- No retry sleeps for settled, absent USB storage; bounded late-device support.
- Derived trust-key cleanup and invalidation of stale signatures/approvals.
- Bounded HTTP connections, overload metrics, and durable status persistence
  outside the transfer-progress lock.
- Configurable VM hardware, installed Secure Boot, host-observed boot timing,
  and opt-in, deadline-bounded, checksum-verified load tests.

## Local static-file benchmark

2026-09-16, WSL2, generic Full filesystem 523,096,064 bytes. Every transfer was
verified against the local artifact. One run per concurrency level; UI tests
were also running on this host. These figures are not a controlled production
LAN comparison or a prediction of physical fleet boot time.

| Clients | Python elapsed | Nginx 1.26.3 elapsed | Verified per server |
|---|---:|---:|---:|
| 1 | 1.459 s | 1.644 s | 1/1 |
| 10 | 8.684 s | 8.798 s | 10/10 |
| 50 | 43.642 s | 47.377 s | 50/50 |

No Nginx advantage was demonstrated in this sample, so no server migration was
made. The benchmark processes/listeners were stopped afterward. The Nginx
package was extracted into a separate local test directory, not installed as
a system service. JSON reports remain under ignored build output.

## Completed image validation

Both generic candidates passed all 29 final-image release gates on 2026-09-16,
with zero failures. The 230-test suite passed against source and each extracted
image. Coverage includes GTK screens at standard/1024×768 resolutions, a real
RDP session, BIOS/UEFI/Secure Boot ISO boot, BIOS/UEFI installation followed by
boot without installation media, PXE with central configuration, and cold/warm
USB cache boot. Warm cache boots requested no filesystem image over HTTP.

Both ISO SHA-256 sidecars passed, and their kernel/initrd/filesystem bytes match
the corresponding PXE artifacts. Configuration is generic with no embedded site
credentials, site trust keys, support authorized keys or SSH host private keys.
Shell/static checks, ShellCheck and default/HTTPS Compose configuration validation
passed. A new container image has not been built or tested with a Docker daemon.

The build outputs and logs are under `out/candidate-1.5.1/` (ignored by Git).
Each profile includes an artifact-bound `pxe/thinclient/verification.json`.

## Supplemental hardware validation

All seven cases passed for both Lite and Full (14/14), using 2 GiB RAM:

- BIOS ISO boot with a baseline `qemu64` CPU and two vCPUs.
- UEFI ISO boot with virtio graphics.
- BIOS PXE with rtl8139 and UEFI PXE with virtio networking.
- SATA/BIOS and NVMe/UEFI installation, followed by boot without install media.
- Installed-disk Secure Boot with Microsoft-enrolled OVMF firmware.

Results, serial logs, screenshots and host-to-UI timings are in each profile's
`hardware-matrix/` directory. Runs were sequential with isolated PXE copies.
These emulate controller families; no physical eMMC, VMD, Wi-Fi, GPU or NIC model
was certified. The optional 1 GiB experiment was not run, and 2 GiB UI readiness
is not a promise that every remote session and peripheral workload fits 2 GiB.

## Remaining site validation

The user's physical target is Dell/HP PCs with 2–4 GB RAM, Gen3–Gen10 (assumed
Intel Core generations). Exact models, NICs and storage are not yet recorded.
The oldest 2 GB and newest 4 GB representatives from both vendors take priority;
see [the fleet test plan](HARDWARE-PERFORMANCE.md#fleet-target-and-test-priority).
The 2 GiB VM results above do not validate those physical PCs or a 4 GB matrix.

Representative physical hardware, actual LAN cold-fleet load, cable-loss recovery
and real peripheral/RDP sessions still require site testing. Select a non-critical
physical client and retain the existing fleet default before any promotion.
The candidate ISOs have not been published or deployed. Pushing the source does
not publish a release or promote the live fleet's default image.
